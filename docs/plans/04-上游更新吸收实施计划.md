# 上游更新吸收实施计划

## 计划定位

本计划用于在个人 `ui-custom` 定制基础上，分三批吸收 `upstream/main` 的近期功能与修复。它记录范围、累计路径、冲突处理、代码责任、验证门槛和阶段证据，不替代 `AGENTS.md`、ADR 或功能规格中的长期契约。

本项目现有 `docs/plans/` 使用历史扁平计划结构，本次不迁移旧计划树、不重编号既有计划；本文件是独立的跨会话实施计划。历史上游合并记录见 [`03-上游v0.9.0合并实施计划.md`](03-上游v0.9.0合并实施计划.md)。

功能和代码约束依据：

- [`AGENTS.md`](../../AGENTS.md)：开发命令、架构不变量、代码地图、个人分支工作流和定制保留边界。
- [`docs/specs/00-规范索引.md`](../specs/00-规范索引.md)：长期功能和规范入口。
- [`01-交互加载性能优化计划.md`](01-交互加载性能优化计划.md)：会话、文件树、Git、Worktree 和聊天切换性能保留能力。
- [`02-Subagent-Web交互控制台实施计划.md`](02-Subagent-Web交互控制台实施计划.md)：Subagent Web 控制台的既有范围，不因上游同步自动扩大或替换。

## 已确认范围与提交策略

- 吸收范围：共同祖先之后上游的功能和修复按三批处理；文档提交只作为事实来源，按最终代码手工同步，不整文件覆盖 `AGENTS.md`。
- 保留范围：本地会话索引/分页/缓存/性能优化、置顶排序、工作树快捷切换与过滤、纵向面板调整、拖拽平滑、工具/技能精准选择、现有主题和交互习惯。
- 非目标：不改变 Pi 会话格式、Subagent Web 功能契约、文件授权边界、项目身份规则、既有性能优化的正确性语义；不做无关重构、部署、推送或 PR。
- 合并方式：不直接 `git merge upstream/main`，不使用整文件 `ours/theirs`；以提交为来源，按功能批次手工移植并逐处保留双方必要行为。
- 回滚点：每批完成并通过该批门槛后创建一个本地 commit；不 push。计划文件不在施工开始前单独提交，首次施工时精确决定是否与第一批一起提交。
- 暂停规则：每批完成后先汇报实际差异、验证和遗留问题；下一批只有在当前批次没有未决阻断时继续。

## 累计可运行基线

主要使用者是通过 Pi Web 浏览、组织和执行 Agent 会话的用户。稳定主入口是 `npm run dev` 启动的 Pi Web（默认 `30141`），不是临时测试页面。

当前累计路径：

```text
启动 Pi Web
→ 选择项目/工作树
→ 浏览会话树和文件区
→ 打开聊天并加载历史
→ 发送消息并观察流式/工具反馈
→ 查看文件、Diff、Git 状态和运行态
```

本次三批更新都必须在这条路径上累计，而不是分别建立临时入口：

```text
现有路径
→ 第一批：运行稳定、跨平台、API/会话/认证修复
→ 第二批：聊天输入、消息展示、Agent 反馈增强
→ 第三批：侧边栏、文件面板、插件面板和响应式布局增强
→ 从同一入口完成累计回归
```

第一批开始前建立完整施工前基线：

```bash
git status --short
git branch --show-current
git log -1 --oneline
node_modules/.bin/tsc --noEmit
npm run lint
npm test
git diff --check
```

第二、三批开始前只复核工作区/分支和上一批回滚点，并运行受影响范围的类型检查、Lint、定向测试与必要 smoke；只有共享 runtime、依赖锁文件或组合根发生影响时，才提前扩大验证。最终收口再统一运行全量 `npm test`。普通批次不因“内容较多”自动重复所有历史浏览器矩阵；按本批 L0/L1 和 L2 运行定向测试及最小累计 smoke。当前已存在的失败必须在施工前记录，不能在批次结束时静默归为本批缺陷。

### 最终累计门槛

第三批完成后，从当前分支和同一稳定入口执行：

- `node_modules/.bin/tsc --noEmit`
- `npm run lint`
- `npm test`
- `git diff --check`
- 与聊天、文件、侧栏、面板和上游变更直接相关的 `npm run test:e2e` 或等价浏览器路径（仅在环境可隔离时执行）。
- 桌面/移动端浏览器验收，确认实际加载的是当前工作树；检查台式布局、窄视口、移动抽屉、面板拖拽、全宽、聊天滚动和文件操作。

不运行 `next build` 作为开发验证；不停止或占用其他 worktree 的服务，不修改真实会话、全局配置、凭证或共享服务状态。

### 失败归因

- 本批实现缺陷或真实回归：阻断当前批次，修复后重新验证。
- 施工前已存在的问题：记录证据；若阻断本批路径，返回讨论，不伪造通过。
- 环境/依赖/服务不稳定：先恢复固定环境，不能通过改业务代码或放宽断言绕过。
- 上游未明确、与本地定制冲突的行为：停止并向用户说明具体可观察差异，等待决定。
- 新增的完整性、并发、恢复或测试要求若无当前契约和风险依据：不自动升级为阻断门槛。

## 停止条件

出现以下任一情况，暂停当前批次并讨论：

1. 无法同时保留本地定制和上游正确性，需要选择一方行为。
2. 需要改变公开 API、会话文件格式、授权/路径安全边界或 Subagent 功能契约。
3. `package-lock.json`/Next 升级导致依赖或开发服务无法稳定复现。
4. 发现来源不明的工作区修改，或需要覆盖 `.pi/`、`.pi-subagents/`、真实会话和全局配置。
5. 冲突修复引入新的共享状态所有者、第二套面板/请求/缓存机制或无关重构。
6. 定向门禁失败无法区分本批回归与环境/存量问题。

## 完成记录规则

每批只有在对应局部和累计门槛通过后，才把该批状态改为“已完成”，并追加：实际变更范围、commit hash、验证摘要、视觉验收结果、延期项和下一批入口。最终三批全部通过后，再判断是否需要按 `sync-project` 增量同步长期规范；不把提交号、临时报错或阶段进度写入 `AGENTS.md` 的长期事实章节。
