# ADR 0006: Native, non-blocking role-task handoff

## Decision

Pi Web hosts the `start-leaf-role-messages-v1` bridge, not the workflow state machine. `GET /api/role-tasks?capabilities=1` is a side-effect-free startup gate. `POST /api/agent/new` accepts an optional `roleTaskPath`; SDK custom entry `pi-web:role-task-binding` restores the path. Only a bound session registers the inline `role_task_message({kind,text})` tool. Its execute handler obtains `ctx.sessionManager.getSessionId()` and sends a JSON stdin request to the fixed `getAgentDir()/skills/start-leaf/scripts/native_call.py` using `execFile("python3", [driver])`. The actual SDK tool-call ID goes in the top-level `call_id` for native retry deduplication; the model message remains only `{kind,text}`. No model-supplied sender, recipient, shell command or script path is used. The tool queues through the Python driver and returns `queued`, never synchronously asks a peer model. The driver is authoritative for work ownership, valid report, mailbox and completion decisions.

The host verifies an absolute regular `任务.json` path under its own real git checkout's `_交付记录/start-leaf/` tree, checks its `project_root` against the git root and session cwd, rejects symlinks at each path component, and refuses other protocol modes. A bound session's tools cannot be switched into a recreated, unbound ID. A freshly created SDK session has no ID before creation: initial binding therefore verifies the task file but the tool refuses messages until the native task has registered its SDK session ID. Reopening a persisted session requires that registered ID. This is trusted host code, **not** an OS sandbox or an authorization system for arbitrary filesystem access.

`POST /api/role-tasks` watch writes an atomic index under the agent runtime directory; a process-global runner Map serializes both periodic and fast checks for each task. The periodic interval follows `task.monitor.interval_seconds` (default 300 seconds); Node instrumentation recovers indexes at startup, and later requests recover as well. First tick and post-message or `agent_end`/`agent_settled` ticks are delayed one second and coalesced. Both message and tick driver calls use a conservative bounded 120-second timeout; a timeout, parse/driver error, or incomplete write is a gap, never task completion or an automatic delivery retry. The Python terminal state `handoff_complete` or a successful tick response with `stop:true` cancels both timers and removes the index; paused work remains observed, with the Python driver responsible for suppressing wakeups. Index and receipt writes use exclusive temporary files, fsync and atomic rename; reads reject substituted symlinks and malformed or noncanonical JSON. Host event handlers never infer completion from `agent_end` alone.

Deliver requires a currently matching mailbox event, current work ID, registered sender/recipient and the recipient's SDK wrapper bound to this task. New messages targeting a worker whose work is `reported` are rejected, including a second task/mailbox check immediately before SDK admission; existing receipts remain readable without starting another run. It uses that wrapper's serialized prompt admission, not `followUp` or `steer`: busy returns `busy`, preserving the Python queue. A durable receipt is written as `uncertain` before submission; only SDK preflight acceptance upgrades it to `delivered`. It proves admission, **not** that the model processed the message. Duplicate event IDs with differing content are rejected; uncertain receipts remain uncertain and are never automatically re-sent. `GET /api/role-tasks?taskPath=...&eventId=...` exposes receipts for reconciliation. A process failure in the narrow gap before the receipt is durable cannot be claimed exactly-once; a first SDK session's custom entries also follow the SDK's normal deferred JSONL flush (until its first assistant message).

The native tool returns the driver's `event_id`, `instruction` and `recipient_id` (when present) with its queued status, so a role knows when to stop rather than spinning. The message is prefixed as program/role handoff, explicitly not a human instruction or authorization. No role-task endpoint creates a fallback fixed prompt on driver failure. The host does not start or manage an external service: timers run only while the existing Next.js process lives.

## Addendum: reopening historical role sessions and per-session model preference

Reopening a persisted role session after an idle-timeout shutdown is an identity check, not a new dispatch. `startRpcSession` accepts a session that the task itself registered: the current dispatcher, the current worker, or any `previous_works`/archived work session, always under the same task path and the same `project_root`/cwd. `boundSession` therefore stays narrow (dispatcher and current worker only) and is still the guard for the inline `role_task_message` execute handler and `POST /api/role-tasks` `deliver`; `restorableSession` adds archived work sessions for reopening only. A persisted binding wins over a different `roleTaskPath`, so one session can never be reopened against another task. The host validates one membership map over dispatcher, current work and archived works before use: professional roles are limited to 施工/审查/验收, archived works must be `reported` and carry a session, a reused session id must keep the same role, and neither an archived professional nor the current worker may be the dispatcher. A session reused from history without declaring its role is rejected as an unspecified conflict, while a legacy current work with no history keeps its previous behavior.

An archived session is a human review chat. A normal `prompt` there must not count as workflow dispatch: the `agent_end`/`agent_settled` idle tick is emitted only while the task is not finished and the calling session is currently bound (`boundSession` re-read on each event), so chatting in a historical session cannot wake old work or a closed handoff. The native tool still refuses a historical caller, and delivery still requires the current work ID and mailbox match.

Model settings remain ordinary UI operations on a role-bound session. `set_model` and `set_thinking_level` append a `pi-web:role-model-preference` custom entry holding the actual `{ version: 1, provider, modelId, thinkingLevel }` after the SDK has applied and clamped it; `max` is a legal `ThinkingLevel` and is accepted. The preference is read from the current tree branch, so a user `navigate`/`fork` follows the visible line and an unmarked SDK `model_change` is never inferred as an override (no history migration). `get_state` returns `roleModelPreference` (the full object or `null`) only for role sessions, so non-role sessions keep their previous shape. Reopening or reloading reads the entry back from the transcript; an existing role session with no entry is treated as having no separate user override, and reading it never rewrites the transcript.

Workflow default alignment calls the same commands with an explicit `roleModelSource: "defaults"`. The marker distinguishes configuration intent only; it is unauthenticated body data, it never records a user preference, and it may not change a state that an existing preference already fixed: a differing default model or thinking level is rejected with code `role_model_preference_locked` (HTTP 409). A defaults `set_model` that resolves to the recorded preference and the already-active model is a true no-op — no SDK `setModel`, so thinking is not reset from the model/global default — while a defaults call that matches the recorded preference but finds a different actual model may restore the preference model. Defaults also require an idle session (`isPromptRunning`/streaming/bash/compacting) and are rejected with `role_model_defaults_busy` otherwise, while an explicit user change is not gated and may run on a busy session. For role sessions both defaults and UI `set_model`/`set_thinking_level` run through one per-wrapper serial queue; a defaults alignment additionally holds the same `acquirePromptAdmission` critical section as `prompt`/`role_task_deliver` from its fresh idle/preference check through the awaited model refresh and SDK setter, releasing it in `finally`. A `send` awaits the queue, so the outer mutating-command guard stays intact and no recursive `send` is involved. Prompt admission checks the defaults marker twice: immediately before queueing (so a caller gets a typed busy now, `role_task_deliver` `busy` and a plain `prompt` `prompt_busy`/`accepted:false`, instead of waiting out the switch and auto-starting late) and again after taking the lock (so a default that started while admission waited cannot be missed); no defaults setter can pass `onAdmitted`. A default that finds a running role rejects `busy` rather than switching it. The idle state and preference are re-checked after the queued wait and after the awaited model refresh. Role-session `get_state` also reports `isModelChanging`, true while any role model/thinking setter (defaults or UI) is enqueued or executing, so read-only inspection sees a transient busy instead of a false idle; non-role responses keep their shape. `setModel` is called without `persist`, so it never rewrites global defaults. Defaults are applied only when no preference entry exists, so the Python driver can keep the user's choice. `GET /api/role-tasks?capabilities=1` advertises `historicalRoleRestore: true` and `roleModelPreference: true` alongside the unchanged `start-leaf-role-messages-v1` protocol for the Skill's pre-dispatch gate; the command body passes `roleModelSource` through `/api/agent/[id]` unchanged.
