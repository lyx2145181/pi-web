# Built-in subagents

## Role model selection

- Profiles use `allow_parent_model_override` (API `allowParentModelOverride`), default false. Saves, copies and enabled PATCH preserve it; an old PUT omitting it retains the stored value.
- For a role with a specified model, create uses that model and ignores parent `Agent.model` unless this switch is on, including unknown or ambiguous ignored parameters. The selected role model must still resolve; it is not silently replaced when unavailable. With no specified model, parent selection or inheritance remains unchanged. An allowed explicit override is per-call, never a profile write.
- The checkbox sits beside the model field and uses the existing draft/Save flow. No-model drafts keep the intent but disable the checkbox with a visible explanation; built-in forms stay read-only.
- Resume retains the child's current model and ignores any attached `Agent.model`, without rejecting or retrying the task. Parent or profile edits do not reassign an existing child, and manual child `set_model` remains available. Cold restoration follows the saved-model rules in [models.md](models.md); no new resource snapshot version or override-permission store is introduced.

## Built-in subagents
- Profiles accept independent, default-off capabilities: `code_mode` / `codeMode` (Code mode) and `load_mcp` / `loadMcp` (MCP) plus a selected list of scoped server identities (`mcp_servers` / `mcpServers`). A v3 snapshot freezes them at spawn; a call never inherits the parent's active Code mode or its connection set (D2), and older snapshots gain neither. A Chat-only profile gains neither either. See [subagent-resources.md](subagent-resources.md) for the API, pre-import scope, scoped transport admission and picker behavior.
- The global `builtInEnabled` in `~/.pi/agent/agents/settings.json` is off when the file or field is absent and when the file is malformed (fail closed); writes are atomic and keep unknown fields. The inline extension factory is always present, so a reload can apply the switch, but registers no tools while off; after changing it the user must reload the session explicitly, and `Agent` dispatch re-checks the setting so a stale call cannot start a subagent. When on, only a recognized legacy `pi-subagents` extension registering a reserved tool (`Agent`, `get_subagent_result`, `steer_subagent`) is removed, along with the conflict errors it caused; unrelated extensions stay. ADR 0003.
- The three tools register with `exposure: "model-only"`, so `ctx.executeTool()` (a codemode script) cannot start, collect or steer a subagent: a script-started run would record the nested call id (`<codemode call>/<n>`) as its `parentToolCallId`, which no transcript entry carries, and the chat would lose its link to the child session. `lib/subagent-extension.integration.test.mjs` pins this against a real `AgentSession`.
- A run stays in `getSubagentRuns()` from dispatch until its result entry is written, so `get()` reports a persisted `running` / `queued` status with no result and no running wrapper as `interrupted`: its process stopped and nothing will finish it (otherwise `get_subagent_result({ wait: true })` polls forever after a restart). `start()` writes the child's session file at dispatch (`persistChildSession()`): pi creates one only once a user or assistant message exists, so a run stopped while queued or connecting MCP servers, or refused for missing credentials, kept its entries in memory only and was gone (from `get()`, `resume` and the sidebar) once its idle wrapper was released. `setSessionFile()` reloads the written file, so pi appends every later entry; a queued run a restart cuts off reads as `interrupted` like a running one. The file is the only record of a settled run: one kept in memory as well would outlive a deleted child, and `resume` would reopen its missing file as a new, unrestricted session in the server's cwd.
- `GET /api/sessions` and `GET /api/sessions/[id]` settle that status the same way, per response (`subagentDisplayStatus()`, `lib/rpc-manager.ts`): a running wrapper reads `running`, a run in the live map its own status (`getLiveSubagentStatus()`; a queued child's idle wrapper may have been released), anything else `settleOrphanedSubagentStatus()`. The cached scan keeps the file's status, so no cache holds a liveness answer, and the switcher and viewer never spin on a run a restart cut off.
- A turn typed into the chat of a child a restart cut off (`POST /api/agent/[id]`; its file still says `running` or `queued`, read as `interrupted`) settles that run when it ends: `settleDirectTurn()` on `agent_settled` writes the result entry, or the child reads `interrupted` for good. The parent is not told. A report wakes its model, and the user is only talking to the child; `get_subagent_result` finds the result. Input that starts no run (a handled extension command) records nothing. A child with a live run or a settled result is left alone, so talking to a finished child keeps its report.
- An id that finds nothing (`get_subagent_result`, `Agent`'s `resume`) is answered with the session's ten latest subagents, read from the `details` on its tool results (`withSubagentCandidates()`), so the model can correct a mistyped id from the error. Only that error changes: reports and other tool output keep naming the full id, and no prompt text is added (#1474 proposed short ids instead; no real session had failed to copy an id).
- Built-in profiles (`general-purpose`, `explore`, `plan`) are switched off by name in that file's `disabledBuiltIns`, never by copying them to a `.md` file (ADR 0005). `builtInProfiles()` stamps `enabled` onto them so the panel, the `Agent` tool description and `resolveSubagentProfile` agree. Writes are minimal edits that keep names they did not touch, including ones no built-in claims; reading fails *open* (the feature switch has already failed closed). `PATCH /api/subagents/profiles` with `scope: "builtin"` writes it; `PUT`/`DELETE` refuse that scope. A same-name file replaces the built-in outright and is switched off through its own frontmatter. Only the switch is live for a built-in; the rest of the form is read-only.
- A positive `max_turns` allows one wrap-up turn only when the SDK would otherwise continue. The limiter chains the SDK's awaited `finishTurn` hook and ends unfinished work without cancelling a completed answer. The wrap-up turn sets `steeringMode` to `all` so a steer queued earlier cannot hold the instruction back. An `end` decision alone does not stop the run: AgentSession starts another run for anything still queued, so the limiter clears the queues, lists those messages in the turn-limit error, and refuses `steer_subagent` from then on. Exhaustion is a failed run with that error and any partial output. A request that ends with `stopReason: "aborted"` is `aborted` even when the controller did not ask for it (Stop in the child's own chat); a provider error is `failed`.
- `Agent`'s foreground completion wait (new runs and resume) and `get_subagent_result({ wait: true })` accept an optional `wait_timeout` in seconds, defaulting to 1800 (30 minutes, `SUBAGENT_WAIT_TIMEOUT_MS`, `lib/subagent-extension.ts`). Choose a longer budget for long tasks. Values are integers from 1 to 2,147,483 seconds (Node's signed 32-bit millisecond timer bound); invalid values are rejected before dispatch or lookup. Foreground completion budgets start after dispatch; result-wait budgets include the first lookup. Background dispatch and `wait: false` lookups return immediately. Expiry returns the last status and session id, and the child keeps running. A foreground wait that expires subscribes to the existing completion promise for a normal parent report, detaches parent cancellation, and stops emitting tool updates; the persisted run keeps its original dispatch mode. Stop before expiry still reaches a foreground child and releases the caller even if the child does not settle. Start/resume handle signals aborted during setup and replay pending cancellation once the queue handle exists, so even a full per-parent queue cannot delay cancellation settlement. Result waits include queued runs and stop polling on expiry, cancellation or completion. `lib/subagent-wait.test.mjs` pins these boundaries, with real SDK start/resume coverage in `lib/subagent-runtime.integration.test.mjs`.
- `notifyParent` skips a run's completion notification when the parent already collected that result with `get_subagent_result`, which marks every terminal result consumed, including originally foreground runs whose wait may have expired. The mark names the run (`sessionId` + `completedAt`), never just the session, since `resume` reuses the session id; `resume` keeps the mark. While the parent `isRunning()` (often still inside that poll) the notification is held and the mark re-checked; an idle parent is notified at once.
- The notification is a `custom` message, which pi's `convertToLlm` replays as a plain `user` turn, so `subagentNotificationText()` prefixes `SUBAGENT_NOTIFICATION_PREFIX`; otherwise compaction files the report under the user's Goal / Constraints. Keep the prefix in code, never in a profile prompt, so the model cannot drop it. A `resume`d run's notification adds a line saying it supersedes the earlier report, which it would otherwise repeat word for word. Foreground `Agent` and `get_subagent_result` results are `toolResult`s and keep the bare `subagentFinalText()`.
- Profile files (`~/.pi/agent/agents/*.md`, project `.pi/agents/*.md`) are shared with other runtimes: saves and copies preserve foreign frontmatter, `ext:` selectors and unedited resource aliases. `skills` / `extensions` selections are applied before SDK imports. V2/v3 snapshots freeze builtin and extension tool authority while admitting approved late registrations; v1 hard allowlists remain unchanged. V3 also freezes independent default-off Code mode/MCP capabilities and selected scoped server identities; older snapshots gain neither capability. Creation, cold restore and reload share the resource/trust policy. See [subagent-resources.md](subagent-resources.md) for the API, scope-preserving settings, execution limits and picker behavior.
- `Agent` resume retains the child's profile, model, thinking level, and context; its continuation prompt, description and background mode can change. An attached `model` is ignored, never rejected — the child keeps its current model. Other nonempty creation options (`thinking`, `input_files`, `inherit_context: true`, `isolation`) and nonzero `max_turns` are rejected before dispatch; empty defaults, including `max_turns: 0`, remain compatible with tool startup. Start a new subagent to change those options.

## What the model may choose when spawning a subagent

- `Agent` offers `subagent_type`, `prompt`, `description`, `run_in_background`, `resume`, `input_files`, `model`, `thinking`, `max_turns`, `inherit_context`, `wait_timeout`, and `isolation` (D1, unchanged from this build). The profile decides when a call omits a value: the runtime reads `thinking` (falling back to the parent's level), `max_turns`, and `inherit_context` from the profile when the call names none. An explicit call value still wins over the profile and reaches the runtime; these parameters are not silently dropped. Explicit `max_turns: 0` means unlimited and overrides a positive role limit.
- `model` resolves as this build always has: the profile's own model is used unless `allow_parent_model_override` permits the call's model (which is then per-call, never a profile write). A reference reads as pi's `--model` does: `provider/modelId` or a bare id, optionally ending in `:<thinking level>` (D3). The whole reference is tried first, so an id that contains a colon (`qwen3:8b`) still matches whole, and a suffix that is no thinking level is never stripped. The thinking priority is an explicit call `thinking`, then the profile's `thinking`, then the chosen model's `:level` suffix, then the parent's level. A protected role (no override) ignores an attached invalid or suffixed model without rejecting the call.
- Resume follows the unchanged creation-option restrictions above; model shorthand is for spawning, not reassigning an existing child. The per-call `wait_timeout` may change on resume.
- `input_files` is sized against the protected role model (or an allowed call override, else the parent), about a tenth of its context window and at most 512 KiB, before creating a worktree or child session. The early lookup is non-throwing; the actual protected selection resolves after approved child services refresh models.json and register their providers, but before creating a child SessionManager. Unknown models still fail rather than falling back.

- A background run's report reaches the parent on its own, so the background `Agent` answer says it need not be collected with `get_subagent_result`, and that tool's description does not read as a status check: a model that polls it gets `is running` back each time and spends turns until the run ends. `wait` stays for a parent that has nothing else to do, such as one collecting several parallel runs; the held notification is then skipped as above.
- An isolated run's `subagentFinalText()` says where its worktree is, since the model reads only `content` (#1202). It goes by whether the worktree path still exists when the run's result entry is written (`recordResult()`), and the entry keeps that as `worktreeExists`, so the child read back from its file says the same. Gone: removed, its branch keeping any commits, also when the checkout was removed during the run and git's removal then failed. Still there after this run's removal was refused for uncommitted or untracked files: kept at its path and branch, for that reason. Still there otherwise: still at its path and branch, with no reason, as after any resumed run (resume removes nothing, and an interrupted run never got to). Never in git's words, which end in `use --force to delete it`. An entry written without the field gets no sentence.

## Agent switcher usage
- Subagent rows keep three lines: task, `profile · modelId · thinkingLevel`, then usage. The model and thinking level come from the active branch's recorded settings (`getSessionSettings()`; assistant-message model fallback for older files), never the profile's defaults, and ride the existing batch stats response/poll. `off` or missing thinking levels are hidden. The profile is capped at 40% when a model is shown; the model truncates before the non-shrinking depth. The metadata tooltip keeps the complete `provider/modelId`, depth and relative update time; main-agent rows and selection/viewer behavior are unchanged. The stats cache includes the leaf id so navigating without appending cannot retain another branch's settings. `app/api/sessions/stats-route.test.mjs` pins the recorded settings, the assistant-message fallback and the leaf change.
- Each row of the agent switcher (main agent and every subagent) shows its active time, total tokens and cost, with the stats popover's breakdown in its tooltip; the header shows their sum. `POST /api/sessions/stats` reads each id as `GET /api/sessions/[id]` does (a live wrapper's entries, else the cached file) and counts like the popover (`computeSessionStats()`, `computeSessionTotalActiveMs()`), never touching an `/api/agent/` route. A summary is kept per SessionManager until its entry count or last entry changes, since the switcher polls every 3 s on a visible page while any agent in the family runs, and reads once more when a run starts or ends. The toolbar's numbers are the main session's alone; the switcher's sum is the only place subagent spend adds up.
- The top bar's Agents button is always there, greyed on a fresh composer. Its badge counts the family's subagents, none at zero, and while any of them runs it counts only those, accent-tinted and ringed by a spinner (`getAgentsBadge()`, `lib/session-family.ts`); the button's title and label say how many run. Running means listed by the sidebar's running poll, as in the switcher's header, so the badge adds no request of its own. A narrow phone (≤480px) folds the chat's other toolbar actions into the More menu but keeps the Agents button outside it, left of More, so its badge stays in sight and the open menu (which starts right of More) never covers it.

## Tab
- The `Agent` card's button opens the child in a right-panel tab (`components/SessionChatPanel.tsx`, the panel side chats use, tab id `agent:<sessionId>`), beside file and terminal tabs: the full chat with its live stream and composer, as when the child is opened as the main chat. The agent switcher above the chat opens a child as the main chat from its row; the row's side-panel button toggles this tab (accent-coloured and filled while the open panel has it, active or not; a click then closes the tab, and the panel with its last tab) and leaves the switcher open, except on phones, where the panel covers the chat.
- One session has one chat: opening a child in the main chat closes its tab, and its row's tab button is then greyed (`AppShell`).
- A tab is a real view of the session, so opening one on a finished child starts a wrapper through the events route, as opening it in the main chat does; the idle timer releases it. While a child just dispatched has no session to read yet, the panel retries. Only the active tab is mounted. Subagent tabs are not persisted and are dropped on every project switch (`changeFileWorkspace()`), while the file tabs are parked; an active subagent tab hands the panel to the restored project's file tabs.


- Opening a child tab initializes only its approved resources and frozen model/permissions; it does not send a prompt automatically. Successful setup may append the SDK's recorded model/thinking initialization entries, never an automatic conversation; rejected model restoration leaves the file untouched. A missing saved model, auth or resource fails closed with the error shown in the chat. File links use the child session as their authorization context, including PDF page fragments. Ordinary `/side` chats follow [side-sessions.md](side-sessions.md), not the subagent snapshot or parent-report rules.
